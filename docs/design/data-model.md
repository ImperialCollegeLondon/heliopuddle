# Data model

SQLAlchemy 2 models with alembic migrations, working on SQLite and Postgres.
All timestamps are UTC: datetime columns use a `UTCDateTime` type that
stores UTC and always returns timezone-aware values (SQLite has no timezone
support). IDs are integers (`BIGINT` on Postgres).

Migrations live in the package (`server/database/migrations`) and are run
programmatically by `server/database/migrate.py` (`upgrade_to_head`,
`is_at_head`, `schema_diffs`, `downgrade_to`), so no `alembic.ini` is needed
at runtime. On SQLite a migration runs with foreign keys switched off (SQLite's
procedure for rebuilding a table that other rows reference, as table rebuilds do)
and `PRAGMA foreign_key_check` must pass before it commits. Run migrations
through these functions, not through `alembic` inside your own transaction.

The migration history was reset to a single initial migration, `0001`, for
the first alpha release. Databases created before the alpha cannot be
upgraded and must be recreated. New migrations are added after `0001`.

These cannot collide with valid relative file paths. Incremental
`incremental_cursor_path = NULL` means the DB-keyset phase is unfinished.
Completion clears the corresponding chain columns.

### `rule_state` (M4)
| Column | Type | Notes |
|---|---|---|
| project_id, rule_name | composite PK | project FK and configured rule name |
| enabled | bool | default true; effective state also requires YAML enabled |
| watermark_at | datetime, nullable | incremental change key timestamp |
| watermark_id | int, nullable | tie-breaker file id |
| last_success_at | datetime, nullable | completed selection window for age crossings |

Indexes on `file(updated_at, id)` and `file_storage_location(updated_at, id)`
serve the two streams that rule and incremental-index pages merge (see
[rules](rules.md)). On SQLite, hp refreshes planner statistics with a bounded
`ANALYZE` at startup and after every finished full index, so the planner
seeks these indexes; Postgres keeps statistics itself. Rule continuations carry
their current selection window/cursor in Prefect parameters.
Completed batches checkpoint these internal parameters on their own tagged
Prefect run, allowing full/age-chain resume when automatic retrigger is off
without another hp state table. The DB watermark and `last_success_at`
validate recovered checkpoints; writes never reset `enabled`.

## Copy states

Ownership and the protocols that move copies between states are in
[operations](operations.md). Columns on `file_storage_location` for this:
`generation` (incremented on every content-changing
transition, and when a move restarts a copy's `arrived_at`), `op_token`, `op_deadline`, `pending_hash`, `pending_size`,
`pending_metadata`, `pending_content_date`, `pending_by` (what an overwrite
applies to the file when it publishes), `pending_staged` (the pending upload
writes a staging path and publishes it because an object already existed) and
`published_token` (the client token whose content a repair published, so its
late complete is answered `200`; cleared by the next content-changing
transition). `move_destination_id` is set on a move's source
copy while it is `deleting`, the verified destination copy that a retried
delete must re-check first (cleared when any other operation takes the copy
or it leaves `deleting`).

M4 transfers reuse `pending` ownership and these pending-content fields.
Publishing a transfer's destination changes only that copy, never the logical
file's hash or timestamp (except a genuine latest flip); no transfer-specific
table or operation column is needed.

| State | Meaning |
|---|---|
| `pending` | with a live token: an upload or transfer is reserved or being written; without a token: known content (has a hash) awaiting verification |
| `available` | present, hash and size verified |
| `overwriting` | owned by an overwrite: old content still valid; new content staged |
| `deleting` | with a token: delete in progress; without: an earlier delete failed |
| `deleted` | removed |
| `missing` | absent from a storage location that does not accept external changes |
| `unknown` | does not match: hash or size mismatch, unexpected change, never-seen file; an operator can accept it |

## `is_latest`

Recomputed for one series in the same guarded transaction as any change that
can alter it (upload complete, overwrite, verify, accept, index, delete),
under the series row lock (`models.recompute_latest`, selecting the top
eligible version in SQL).

- **Eligible files:** live files with at least one copy that is `available`,
  `overwriting`, or `pending` without a token. Files whose copies are all
  `unknown`, `missing`, `deleting`, `deleted` or token-holding `pending` are
  listed but never latest.
- **Ordering:** the highest `version_number` when `series.version_type` is
  `number`, or the highest `version_text` when it is `text`; unversioned rows
  rank lowest; ties go to the newest `created_at`, then the highest id. A
  series never mixes kinds (see [versioning](versioning.md#one-kind-per-series)).
  Unversioned paths are alone in their literal series (a deleted path re-added
  later shares the series with its deleted rows).
- `series.latest_file_id` points at the latest file, or is NULL when the series
  has no eligible file. Changing `is_latest` updates `updated_at` on every
  file whose flag flips, so incremental rules observe both sides of the
  change. Recomputing unchanged flags leaves timestamps alone (M4, R7).

### `user` (M5A)

Local-mode users ([auth](auth.md)). Not used in `oidc` or `header` mode.

| Column | Type | Notes |
|---|---|---|
| id | int PK | |
| username | str | 1 to 255 ASCII letters, digits and `. _ @ + -`, starting with a letter or digit; unique ignoring case (a unique index on `lower(username)`, which SQL and Python agree on for ASCII) |
| password_hash | str | argon2; never returned by the API |
| roles | JSON list of str | `hp-admin`, or `hp-reader`, `hp-writer`, `hp-deleter`, `hp-operator`, `hp-client-storage-read-write` with an optional `:<project>` |
| is_active | bool | default true |
| credentials_changed_at | datetime | the credentials version (in microseconds): a token is valid only while its `cv` equals it, so a password change or reset invalidates earlier tokens |

| last_login_at | datetime, nullable | set by `POST /auth/token` |

`created_by` and `updated_by` on `file` hold the username (`local`, `oidc`) or
the header value (`header`); they are plain strings with no foreign key, so
deleting a user keeps the history.
